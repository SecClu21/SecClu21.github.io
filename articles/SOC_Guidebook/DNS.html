DNS for SOC Analysts: Detection, Investigation, and Response

A practical guide to understanding DNS, recognizing common attack patterns, and using DNS evidence to investigate suspicious activity.

Introduction

Domain Name System (DNS) is often described as the “phone book” of the internet, mapping human friendly domain names to IP addresses so clients can find resources across networks. This naming layer is what allows users to type example.com instead of memorizing IPs and still reach web servers, APIs, or internal applications. When DNS was originally designed, its creators did not anticipate modern attackers abusing its open, unauthenticated nature, or defenders trying to monitor it for subtle signs of compromise.

As environments grew more complex, DNS became deeply embedded in how operating systems, applications, and services discover each other. Today, adversaries misuse DNS for command and control (C2) communication, data exfiltration, phishing infrastructure, and domain generation algorithms (DGAs), while defenders treat DNS logs and traffic patterns as a critical source of detection signals. At the same time, DNS is essential to normal network operations and cannot simply be blocked or disabled, which makes understanding normal behavior—and how attackers twist it—especially important for early career defenders.

Security enhancements like DNS over TLS (DoT), DNS over HTTPS (DoH), and DNS Security Extensions (DNSSEC) were introduced to protect different parts of the DNS ecosystem, but they do not replace the need to understand plain DNS behavior. This guide takes a practical view of DNS from a defender’s perspective, connecting core concepts to common abuse patterns and the kinds of evidence you will see in logs and network data during real investigations.

What DNS Is

DNS functions as a naming and lookup service for modern networks. Because name resolution typically occurs before a connection is established, DNS requests reveal what a system is attempting to locate, even if the subsequent connection never occurs. This ability to expose intended destinations makes DNS an important source of context during investigations and threat hunting. To understand why DNS provides this visibility, it helps to first understand how DNS resolution works.

How DNS Works

When an application needs to communicate with a resource identified by a domain name, it first checks whether the requested information is already available in a local cache. If no valid cached entry exists, the system sends a query to a configured DNS resolver, which may answer from its own cache or perform additional lookups before returning a response. Once the requested information is received, the client can use it to establish a connection to the destination service.

The returned records are typically cached according to their Time to Live (TTL) values to reduce the number of repeated queries. Although this process usually occurs in the background and takes only milliseconds, it generates a series of requests and responses that can be recorded in DNS logs, packet captures, and other network telemetry. For defenders, these records provide visibility into what systems attempted to locate, when the requests occurred, how often they were made, and whether the responses appear consistent with expected behavior.

DNS Attack Patterns and Indicators

Most DNS traffic in an environment is legitimate, which makes understanding normal behavior an important part of DNS analysis. Rather than focusing on individual queries in isolation, analysts often look for patterns across hosts, domains, timing, record types, and response behavior. The examples below highlight common ways attackers abuse DNS and the indicators defenders can use to identify activity that warrants further investigation.

Malware C2 Over DNS

Some malware abuses DNS as part of its command-and-control (C2) communications to locate attacker-controlled infrastructure or exchange information with it. Because DNS is essential to normal network operations and generates a constant stream of legitimate traffic, malicious DNS activity can blend into expected network behavior, making it more difficult to identify than attacks that rely on less common protocols.

Patterns: Malware may periodically resolve domains associated with its C2 infrastructure before establishing a connection or, in more advanced cases, use DNS queries and responses themselves as a covert communication channel. These lookups often blend with normal name resolution activity and may involve algorithmically generated domain names (DGAs), rapidly changing subdomains, or repeated queries to the same destination.

Indicators: Repeated DNS queries from a single host to algorithmic-looking domains, bursts of NXDOMAIN responses before a successful resolution, or DNS requests occurring at regular intervals regardless of user activity may indicate beaconing behavior. Analysts should also look for unusually frequent DNS requests, repeated queries for uncommon record types, and endpoint telemetry that correlates suspicious processes with the observed DNS activity. While none of these indicators alone confirm malicious activity, multiple indicators occurring together can significantly increase confidence that the system is communicating with attacker-controlled infrastructure.

DNS Tunneling and Data Exfiltration

DNS tunneling abuses the DNS protocol as a communication channel rather than simply using it to resolve domain names. Instead of carrying only legitimate DNS requests, attackers encode commands or stolen data within DNS queries and responses, allowing information to pass through systems that may permit DNS traffic while restricting other protocols. Because DNS is widely trusted and essential to normal operations, this technique can be difficult to detect without careful analysis of DNS activity.

Patterns: Attackers typically encode data within subdomains or DNS record data, most commonly using TXT records, although other record types may also be abused. Successful tunneling often generates unusually long or high-entropy subdomains, frequent queries to the same domain with constantly changing subdomains, and a sustained volume of DNS requests that is inconsistent with normal name resolution.

Indicators: Very long subdomain labels containing random-looking or encoded characters, an unusually high number of TXT or other uncommon record type queries from a single host, and DNS query volumes that are disproportionately large compared to the system's normal activity may indicate tunneling. Resolver logs showing repeated requests to the same domain with constantly changing subdomains, particularly when combined with endpoint or network telemetry, provide strong evidence that DNS is being used as a covert communication channel.

DNS Hijacking and Spoofing

DNS hijacking and spoofing manipulate the DNS resolution process so that users are directed to attacker-controlled infrastructure instead of the legitimate destination. Rather than abusing DNS as a communication channel, these techniques alter or falsify DNS information to redirect traffic, intercept communications, or facilitate phishing and credential theft. Because users often enter the correct domain name, these attacks can be difficult to recognize without examining DNS activity.

Patterns: Attackers may compromise DNS resolvers, poison DNS caches, spoof DNS responses, or modify authoritative DNS records to return malicious IP addresses for legitimate domains. Depending on the attack, victims may be redirected to phishing pages, malware-hosting infrastructure, or attacker-controlled servers that closely resemble the intended destination.

Indicators: DNS responses for well-known domains resolving to unexpected IP ranges, sudden changes in NS, A, or other critical DNS records, and inconsistent responses between trusted resolvers may indicate DNS manipulation. User reports of legitimate websites appearing unusual, unexpected certificate warnings, or authentication failures combined with DNS logs showing new or unfamiliar IP addresses for those domains are strong indicators that DNS hijacking or spoofing should be investigated.

Fast Flux and Dynamic Hosting

Fast Flux is a technique used by attackers to increase the resilience of malicious infrastructure by rapidly changing the IP addresses associated with a domain. Rather than relying on a single server, the attacker distributes services across many compromised or attacker-controlled systems, making it more difficult for defenders to block, disrupt, or take down the infrastructure. This approach is commonly used to support phishing campaigns, malware distribution, and command-and-control infrastructure.

Patterns: A single domain rapidly cycles through many different IP addresses, often spanning multiple networks, ISPs, or geographic regions. DNS responses typically use short TTL values to force clients and resolvers to request updated records more frequently, allowing the attacker to continually rotate the infrastructure behind the domain.

Indicators: DNS logs showing a domain resolving to numerous IP addresses within a short period of time, consistently low TTL values, and IPs associated with previously identified malicious infrastructure may indicate Fast Flux activity. Domains linked to phishing or malware that exhibit continuous IP rotation, particularly across multiple autonomous systems or geographic locations, are strong indicators that the infrastructure is intentionally designed to resist detection and takedown efforts.

Suspicious Use of TXT and Other Uncommon Records

Most DNS record types serve legitimate purposes, and TXT records are widely used to support services such as SPF, DKIM, domain verification, and other application configurations. However, because TXT records can store arbitrary text, attackers may abuse them to distribute malware configuration data, encryption keys, command-and-control instructions, or other information. Less frequently used record types may also be abused to conceal data or evade detection by blending into normal DNS activity.

Patterns: Attackers may use TXT records to retrieve encoded data, malware configuration, or commands without relying on traditional web traffic. Other uncommon record types may be abused in similar ways, particularly when the information being exchanged does not fit normal DNS behavior or appears unrelated to the domain's expected purpose.

Indicators: An unusually high volume of TXT or other uncommon record type queries from a single host, repeated lookups to the same domains for TXT records outside of expected email or service configuration activity, or TXT responses containing unusually large or encoded-looking data may warrant investigation. When these patterns are accompanied by suspicious processes, beaconing behavior, or other anomalous DNS activity, they may indicate malware using DNS to retrieve or exchange information.

Anomalous Resolver Usage and Exfiltration via External Resolvers

Organizations typically configure systems to use internal DNS resolvers so that DNS activity can be monitored, logged, filtered, and managed according to security policies. Attackers may attempt to bypass these controls by sending DNS requests directly to external public resolvers or attacker-controlled DNS infrastructure. Doing so can reduce an organization's visibility into malicious activity while enabling command-and-control communications, data exfiltration, or access to malicious domains.

Patterns: Compromised hosts may send DNS queries directly to external recursive resolvers instead of the organization's designated DNS servers. Attackers may also leverage encrypted DNS protocols, attacker-controlled resolvers, or non-standard communication paths to evade DNS logging, filtering, and monitoring while continuing to resolve malicious infrastructure.

Indicators: : Internal endpoints making DNS requests directly to external resolver IP addresses instead of the organization's approved recursive resolvers may indicate attempts to bypass security controls. DNS traffic using unexpected ports, encrypted DNS services such as DNS over HTTPS (DoH), or resolver destinations that deviate from established baselines should be investigated. When combined with unusual query volumes, suspicious domains, or other DNS anomalies, these behaviors may indicate attempts to evade internal monitoring or facilitate command-and-control communications and data exfiltration.

Analysis and Practical Exercises

Recognizing suspicious DNS patterns is only the first step in an investigation. Analysts must also know where DNS activity can be observed, how to interpret it, and how to correlate information from multiple sources before determining whether activity is legitimate or malicious. DNS evidence appears throughout modern environments, including DNS infrastructure, endpoint telemetry, packet captures, centralized logging platforms, and network security devices. The sections below introduce common sources of DNS evidence, explain the unique perspective each provides during an investigation, and include Skill Builders to help readers begin applying these concepts in practical ways.

Key Information:

  • Client IP or hostname – Identifies the system making the DNS request.
  • Query name (domain) – Shows which domain the client attempted to resolve.
  • Record type (A, AAAA, MX, TXT, etc.) - Indicates the type of DNS information requested.
  • Response code (NOERROR, NXDOMAIN, SERVFAIL, etc.) – Shows whether the lookup succeeded or failed.
  • Returned IP address(es) – Identifies the destination provided by the resolver.

Common Findings:

  • High NXDOMAIN rates from a single host, which may indicate a domain generation algorithm (DGA), malware, or a misconfigured application.
  • Unusually long or high-entropy subdomains that may suggest DNS tunneling or encoded data.
  • Unexpected DNS activity originating from systems that normally generate little or no DNS traffic.
  • Repeated lookups for suspicious domains, uncommon record types, or rapidly changing subdomains.

Skill Builder: Use nslookup or dig to resolve several common websites and compare the results for different record types, such as A, AAAA, MX, or TXT records. Before examining any logs, consider what DNS activity you would expect these lookups to generate. If you have access to DNS logs through a home router, Pi-hole, DNS server, home lab, or public sample dataset, compare your expectations with the recorded activity. If DNS logs are unavailable, use Wireshark to observe the same queries and responses. Focus on recognizing what normal DNS activity looks like before trying to identify suspicious behavior.

SIEM and Log Correlation

DNS activity rarely tells the complete story on its own. Analysts use SIEM platforms to correlate DNS events with firewall logs, endpoint telemetry, authentication records, threat intelligence, and other security data to determine whether suspicious queries are part of a larger attack. Viewing DNS activity alongside related evidence helps analysts identify broader attack patterns, prioritize alerts, and make more informed investigative decisions.

Key Information:

  • DNS queries and responses – Shows which domains were requested, by whom, and when.
  • Host and user context – Associates DNS activity with specific systems and users.
  • Correlated security events – Connects DNS activity with endpoint alerts, firewall logs, authentication events, and other telemetry.
  • Threat intelligence matches – Identifies domains or IP addresses associated with known malicious infrastructure.
  • Historical searches – Allows analysts to review past activity and identify trends over time.

Common Findings:

  • High NXDOMAIN rates or algorithmically generated domain names that may indicate a domain generation algorithm (DGA).
  • Excessive TXT or other uncommon record type lookups that could suggest DNS tunneling or malware configuration retrieval.
  • Internal systems sending DNS requests directly to external resolvers instead of approved organizational DNS servers.
  • Multiple hosts communicating with the same suspicious domain, indicating a potentially broader compromise.

Skill Builder: Think about the information you would need to investigate a suspicious domain. Besides DNS logs, what other evidence would help you determine whether the activity is legitimate or malicious? Make a list of the data sources you would want to examine—such as endpoint telemetry, firewall logs, authentication events, or threat intelligence—and briefly explain what question each source could answer. This exercise helps build the habit of correlating multiple sources of evidence rather than relying on a single log.

Packet Captures and Protocol Analysis

Packet captures allow analysts to examine DNS communications exactly as they occurred on the network, making them valuable for validating suspicious activity identified through logs or alerts. By inspecting individual queries and responses, analysts can confirm protocol behavior, identify anomalies, and determine whether observed DNS activity aligns with expected operation or requires further investigation. This packet-level perspective often answers questions that summarized log data cannot.

Key Information:

  • Query and response details – View the complete DNS request and response, including queried domains, returned records, and response codes.
  • Protocol fields – Examine DNS flags, transaction IDs, recursion settings, and other header information.
  • Transport details – Determine whether DNS is using UDP or TCP while observing packet sizes, timing, and communication patterns.
  • Query structure – Analyze subdomain length, record types, and other characteristics that may indicate suspicious activity.

Common Findings:

  • Unusually long or high-entropy subdomains that may indicate DNS tunneling or encoded data.
  • DNS queries or responses that are significantly larger or more frequent than expected for normal client activity.
  • Signs of spoofing or manipulation, such as unexpected response sources or mismatched transaction IDs.
  • DNS traffic using TCP for activities such as zone transfers or unusually large DNS responses.

Skill Builder: Consider what happens after an application requests a domain name. Before opening a packet capture, list the sequence of events you expect to occur from DNS resolution through the initial network connection. Then review a packet capture—either one you create yourself using Wireshark or a publicly available sample—and compare it to your expectations. Identify where the DNS query occurs, when the response is received, and how the client uses that information to establish the next network connection.

Endpoint / EDR Telemetry

Network evidence shows that DNS activity occurred, but endpoint telemetry helps explain what generated those requests. Analysts use endpoint data to identify the processes, applications, services, or users responsible for DNS lookups, providing valuable context that is unavailable through network evidence alone. Combining endpoint and network evidence allows analysts to distinguish expected system behavior from suspicious or malicious activity.

Key Information:

  • Process information – Identifies the executable or script responsible for generating the DNS request.
  • Process hierarchy – Shows parent and child process relationships that help explain how the activity originated.
  • User context – Associates DNS activity with the logged-on user or service account.
  • Related endpoint activity – Correlates DNS requests with file modifications, network connections, registry changes, scheduled tasks, or other endpoint events.

Common Findings:

  • Unknown or unexpected processes generating DNS requests.
  • DNS activity that closely aligns with suspicious process execution or persistence mechanisms.
  • Multiple suspicious behaviors originating from the same process, such as DNS queries followed by outbound network connections or file modifications.
  • Legitimate administrative or security tools generating DNS activity that initially appears suspicious but can be explained through endpoint context.

Skill Builder: Open several applications you use regularly, such as a web browser, email client, messaging application, or game launcher, and think about the DNS activity each might generate. Consider which domains each application would likely contact and why. If you have access to endpoint telemetry through tools such as Sysmon, Microsoft Defender, or another monitoring solution, compare your expectations to the recorded process and network activity. Focus on understanding how endpoint telemetry helps attribute DNS requests to the application or process that generated them.

DNS Controls and Network Enforcement

DNS security controls not only protect organizations from malicious domains but also generate valuable evidence during investigations. Analysts use alerts and logs produced by DNS filtering, sinkholes, protective DNS services, and other enforcement mechanisms to identify blocked communications, investigate attempted connections to malicious infrastructure, and better understand attacker behavior. Examining these controls alongside other evidence sources helps analysts determine whether defensive measures successfully interrupted suspicious activity or whether additional investigation is required.

Key Information:

  • Internal recursive resolvers – Centralize DNS resolution, enforce organizational policies, and provide a consistent source of DNS logs.
  • Firewall and network policies – Restrict outbound DNS traffic to approved resolvers and help prevent unauthorized DNS communication.
  • DNS filtering – Blocks or redirects requests to known malicious or prohibited domains based on organizational policy.
  • Encrypted DNS policies – Determine whether technologies such as DNS over HTTPS (DoH) or DNS over TLS (DoT) are permitted, restricted, or monitored within the environment.

Common Findings:

  • Endpoints sending DNS requests directly to external public resolvers instead of approved internal resolvers.
  • Attempts to bypass DNS filtering or network policies using unauthorized encrypted DNS services.
  • Systems repeatedly querying blocked or known malicious domains.
  • Policy violations that explain unexpected DNS behavior without indicating a system compromise.

Skill Builder: Choose a website or online service you use regularly and think about what would happen if your organization blocked access to it through DNS. Consider how the request would differ from a successful lookup, what evidence might appear in DNS logs, and how the user would experience the block. Then research one DNS security solution, such as Quad9, Cisco Umbrella, or Cloudflare Gateway, and compare the types of protections it provides against the attack techniques discussed in this guide.

SOC Analyst Perspective

Understanding how DNS functions is only part of a DNS investigation. The next step is learning how to interpret DNS activity during an investigation. Alerts provide a starting point, but they rarely identify the root cause of suspicious activity on their own. Analysts must validate the reported behavior, examine the available evidence, and determine whether the observed activity is consistent with normal network operations, a configuration issue, or malicious activity.

The workflows below demonstrate a structured approach to investigating several common DNS-related attack patterns. While the examples discuss potential mitigation strategies, the specific actions an analyst performs depend on organizational roles, responsibilities, and established incident response procedures. Regardless of the environment, successful DNS investigations rely on validating alerts, correlating evidence from multiple sources, and developing confidence in the conclusions before taking action.

Investigating High NXDOMAIN Rates

High volumes of NXDOMAIN responses do not automatically indicate malicious activity. They may result from malware using a Domain Generation Algorithm (DGA), misconfigured applications, typographical errors, or recent infrastructure changes. The analyst's goal is to determine why the failed lookups are occurring and whether they represent an operational issue, a configuration problem, user behavior, or malicious activity.

First — Identify hosts with elevated NXDOMAIN activity using DNS or SIEM logs. Begin by identifying the systems associated with the alert and determine whether they are generating significantly more NXDOMAIN responses than similar systems during the same time period. Compare the volume and distribution of failed lookups against the system's normal behavior to determine whether the activity is unusual for that environment. As you characterize the activity, determine whether the failed lookups originate from a single host, multiple related systems, or a broader segment of the network, as these observations establish the scope of the activity before moving into deeper analysis.

Then — Analyze the queried domains for suspicious or unusual patterns. Determine whether the failed lookups appear algorithmic (random-looking domain names), resemble typographical errors, or target legitimate internal resources that no longer exist. Multiple failed lookups for random-looking domains under the same top-level domain (TLD) may indicate DGA activity, whereas repeated queries for misspelled internal domains often point to configuration or application issues.

Finally — Determine the appropriate mitigation. The appropriate response depends on the underlying cause of the failed lookups. Malware or DGA activity may require host isolation and incident response, while misconfigured applications, outdated DNS records, or typographical errors are often resolved through configuration changes or user education. Continue monitoring to verify that NXDOMAIN rates return to expected levels after corrective actions are taken.

Investigating Suspected DNS Tunneling

DNS tunneling attempts to disguise data transfers within legitimate DNS traffic, making it a common technique for command-and-control (C2) communication and data exfiltration. However, unusual DNS queries do not automatically indicate tunneling, as some legitimate applications generate long subdomains, frequent TXT record lookups, or high volumes of DNS requests. The analyst's goal is to determine whether the observed activity is consistent with normal application behavior or represents an attempt to bypass network controls.

First — Identify hosts with unusual DNS query characteristics. Identify the hosts generating unusually long subdomains, high volumes of TXT (or other uncommon) record lookups, or DNS traffic that is disproportionate to their normal activity. Compare the observed activity with similar systems and the host's own typical DNS usage to determine whether the pattern is unusual for the environment. Characterize the activity by considering which hosts are affected, how frequently the queries occur, and which DNS characteristics appear consistently across the activity.

Then — Examine domains and query patterns. Examine whether the affected hosts repeatedly query a small number of domains while changing only the subdomain, particularly when those subdomains contain long or high-entropy strings. Compare the query patterns across the affected hosts and determine whether the same domains, subdomain structures, or other characteristics recur throughout the activity. Correlate these patterns with available packet captures and endpoint telemetry to determine whether the activity is associated with a legitimate application or process, and consider whether the domains are associated with known services, recently registered infrastructure, or previously identified malicious activity.

Finally — Determine the appropriate mitigation. If the available evidence supports suspected DNS tunneling, determine how the activity can be interrupted while minimizing disruption to legitimate users and services. Potential actions may include blocking the malicious domains, restricting suspicious DNS record types where appropriate, isolating affected hosts, or working with network and incident response teams to contain compromised systems. Continue monitoring to verify that the suspicious DNS activity has stopped and that any corrective actions have not disrupted legitimate DNS activity.

Investigating Suspected DNS Hijacking

DNS hijacking redirects users to unintended destinations by altering DNS responses or manipulating the systems responsible for name resolution. While this behavior may indicate malicious activity, unexpected DNS results can also stem from legitimate infrastructure changes, DNS propagation, load balancing, or configuration errors. The analyst's goal is to determine whether the observed DNS responses are expected or whether they indicate unauthorized manipulation.

First — Validate the reported activity. Identify the domain or hostname involved in the alert and establish what DNS response the affected system received. Compare the returned A, AAAA, or other relevant records and resolved IP addresses with the destination the system was expected to reach, while considering whether recent infrastructure changes, DNS propagation, load balancing, or configuration changes could explain the difference. Determine whether the unexpected result is isolated to a single system or appears across multiple systems using the same DNS infrastructure.

Then — Verify the DNS responses against trusted sources. Compare the returned DNS records and resolved IP addresses with trusted sources to determine whether the affected system was directed to the expected destination. If the responses differ, investigate whether the discrepancy is consistent with legitimate operational changes, such as DNS propagation, load balancing, or configuration changes, or whether the evidence suggests unauthorized manipulation. Correlate the DNS responses with other available evidence, such as resolver behavior and the scope of affected systems, to determine whether the discrepancy is isolated or part of a broader compromise.

Finally — Determine the appropriate mitigation. If the evidence suggests unauthorized DNS manipulation, determine what must be corrected to restore expected DNS resolution. Depending on the cause, this may include flushing poisoned DNS caches, restoring correct DNS records, removing unauthorized resolver settings, correcting compromised hosts file entries, blocking access to malicious infrastructure, or coordinating with DNS administrators to remediate affected systems. Continue monitoring to verify that users are receiving the expected DNS responses after corrective actions are taken.

The specific evidence and investigative questions vary depending on the DNS behavior being examined, but the underlying process remains consistent: establish what is occurring, analyze the evidence that can explain the behavior, and determine an appropriate response based on the findings. The investigations in this section demonstrate how understanding DNS behavior allows analysts to move beyond recognizing suspicious activity and begin determining what that activity means in context. With that foundation established, the article can now return to the broader role DNS plays in network communication and security.

Conclusion

DNS plays a critical role in modern networks and often provides some of the earliest insight into what systems are attempting to communicate with. For SOC analysts, understanding how DNS functions, recognizing common abuse techniques, and interpreting DNS telemetry provide valuable context for identifying suspicious activity and supporting broader investigations. Because DNS activity is present across so many network interactions, learning to interpret its patterns can help analysts connect seemingly isolated events to broader activity occurring within an environment.

While DNS provides valuable visibility, effective investigations depend on understanding the broader context surrounding the activity. Analysts develop confidence in their conclusions by validating observations, considering legitimate explanations, and correlating DNS evidence with other available telemetry before determining the appropriate response. The same DNS pattern may have very different implications depending on the systems involved, the surrounding network activity, and the evidence available to explain what is occurring.

As you continue studying networking and cybersecurity, focus on understanding not only how protocols function, but also how analysts use them during real investigations. Developing the habit of asking questions, validating assumptions, and correlating evidence will be just as valuable as learning the technical details themselves. These habits will continue to apply as you encounter new protocols, technologies, and investigative challenges throughout your cybersecurity career.
