TCP and UDP for SOC Analysts: Detection, Investigation, and Traffic Analysis

A practical guide to understanding TCP and UDP, recognizing suspicious network traffic, and using protocol behavior to investigate security events.

Introduction

Transmission Control Protocol (TCP) and User Datagram Protocol (UDP) form the foundation of most modern network communication. Whether a user is browsing a website, streaming video, sending email, or resolving a domain name, one of these transport protocols is usually responsible for moving data between systems. Nearly every networked device relies on TCP or UDP to communicate, making it essential to understand how these protocols normally behave before interpreting the traffic they generate.

Attackers also rely on TCP and UDP throughout their operations, using the same transport protocols that support legitimate network communication to achieve their objectives. Normal and malicious activity often use the same transport protocols, requiring analysts to understand expected protocol behavior before they can accurately interpret suspicious network traffic. This understanding enables analysts to recognize unusual behavior, identify the evidence needed to investigate it, and determine whether the observed activity has a legitimate explanation or requires additional investigation.

This guide begins by explaining the fundamental differences between TCP and UDP before exploring why those differences matter during security investigations. From there, it examines common attack patterns, the sources of protocol evidence analysts rely on, and the investigative thought process used to evaluate suspicious network activity. Rather than simply teaching how TCP and UDP function, the goal is to help readers develop the analytical mindset needed to interpret network traffic as a cybersecurity defender.

What TCP and UDP Are

TCP and UDP are the two primary transport layer protocols used to move data between systems across IP networks. Although they perform the same general function—transporting application data—they take very different approaches to communication. TCP prioritizes reliable, ordered delivery, while UDP prioritizes speed and efficiency by minimizing communication overhead.

These differences influence how applications use each protocol and, in turn, the types of network behavior analysts observe during investigations. TCP and UDP support most modern network communication, so they appear throughout packet captures, firewall logs, intrusion detection system (IDS) alerts, Security Information and Event Management (SIEM) platforms, and other sources of network telemetry. Recognizing which protocol generated the observed traffic provides important context for interpreting network activity during an investigation.

To understand why TCP and UDP produce different traffic patterns and require different investigative approaches, it is important to first understand how each protocol communicates across the network. Although both protocols transport application data, they use fundamentally different communication methods to accomplish that task. Those differences shape the network behavior analysts observe and provide the foundation for understanding the attack patterns and investigative techniques discussed later in this guide.

How TCP and UDP Work

Although TCP and UDP both transport application data across IP networks, they do so in fundamentally different ways. These design choices affect not only application performance but also the evidence analysts encounter during investigations. Understanding how each protocol behaves helps explain why analysts investigate TCP and UDP activity differently.

Before TCP transfers any data, it establishes a connection through a three-way handshake. The client begins by sending a synchronization (SYN) packet, the server acknowledges with a synchronization-acknowledgment (SYN-ACK), and the client completes the process with an acknowledgment (ACK). Once the connection is established, TCP uses sequence numbers and acknowledgments to track data delivery and maintain the correct order of the data stream. If data is lost or not acknowledged, TCP can retransmit the missing data to support reliable communication.

UDP takes a much simpler approach. Rather than establishing a connection, it immediately sends independent packets, called datagrams, to the destination without verifying that they arrive or are received in order. This lightweight design reduces communication overhead and makes UDP well suited for applications such as DNS, Voice over IP (VoIP), video streaming, and online gaming, where low latency is often more important than perfect reliability.

The different communication methods used by TCP and UDP produce distinct traffic patterns that become valuable sources of investigative evidence. TCP's predictable connection lifecycle generates evidence such as connection establishment, acknowledgments, retransmissions, and session termination that can be observed in packet captures and connection logs. Without a connection state, UDP investigations rely more heavily on communication patterns, packet volume, timing, destination services, and the surrounding context to determine whether observed activity is consistent with normal network behavior.

Common TCP and UDP Attack Patterns and Indicators

The traffic patterns produced by TCP and UDP become meaningful only when viewed in context. Most TCP and UDP traffic in an environment supports legitimate network communication, making context an important part of every investigation. Rather than relying on a single packet or connection, analysts look for patterns, which describe repeated or unusual behaviors that may indicate suspicious activity. They then evaluate indicators, the observable pieces of evidence used to determine whether those patterns reflect legitimate activity or a potential security incident.

While indicators can suggest suspicious activity, they do not confirm that an attack is occurring. Analysts correlate multiple sources of evidence, consider legitimate explanations, and evaluate the surrounding context before determining whether activity warrants further investigation. The examples below highlight common ways attackers abuse TCP and UDP, along with the patterns and indicators analysts use to evaluate suspicious network activity.

TCP Attack Patterns

SYN Flood

A SYN flood is a denial-of-service (DoS) attack that attempts to exhaust server resources by sending large numbers of TCP synchronization (SYN) packets without completing the TCP three-way handshake. Each incomplete connection consumes server resources while waiting for the final acknowledgment (ACK), eventually limiting the server's ability to establish new connections with legitimate clients.

Patterns: Rather than completing the TCP connection process, an attacker continuously initiates new connection requests that remain unfinished. Analysts may observe a sustained increase in SYN packets with comparatively few completed handshakes, resulting in an increasing number of half-open connections on the target system. During distributed attacks, these connection attempts often originate from multiple source IP addresses, making the activity appear to come from many systems simultaneously.

Indicators: Analysts may observe unusually high numbers of SYN packets with comparatively few completed handshakes, incomplete TCP connections, or connections remaining in the SYN_RECV state in firewall logs, IDS alerts, or packet captures. While these indicators are consistent with SYN flood activity, they do not confirm that an attack is occurring. Temporary traffic spikes, load testing, or application and network issues can produce similar observations. Analysts should correlate multiple sources of evidence and consider the surrounding context before determining whether the volume of incomplete connection attempts reflects a malicious attempt to exhaust resources or a legitimate traffic condition.

TCP Port Scanning

Port scanning is a reconnaissance technique used to identify open ports and services on a target system before attempting further activity. By determining which services are accessible, attackers can identify potential entry points, while defenders use the same technique for legitimate purposes such as security assessments, vulnerability management, and network inventory. For analysts, the objective is to determine whether the observed scanning activity represents expected administrative behavior or unauthorized reconnaissance.

Patterns: TCP port scans often generate numerous connection attempts across multiple ports on a single host or the same port across multiple hosts within a short period. The observed pattern often depends on the available telemetry. Analysts reviewing an endpoint may observe a single source probing numerous TCP ports on one system, while network devices often reveal the same TCP ports being probed across multiple systems from a single source. Depending on the scanning technique, analysts may observe completed TCP connections or repeated SYN packets that are intentionally left incomplete. The activity often follows a sequential or otherwise systematic pattern that differs from normal application traffic.

Indicators: Analysts may observe repeated connection attempts from the same source, sequential destination ports, or activity targeting multiple systems in rapid succession in firewall logs, IDS alerts, or network traffic captures. Endpoint telemetry can provide additional context when the scan targets a specific system or originates from an internal host. While these indicators can suggest reconnaissance, they do not confirm malicious intent. Vulnerability scanners, asset discovery tools, network administrators, and authorized penetration tests often generate similar traffic. Analysts should correlate the scanning activity with known administrative tools, authorized assessments, and the systems involved before determining whether the observed probing represents expected reconnaissance activity or an unauthorized attempt to identify accessible services.

TCP Reset Attacks

A TCP Reset (RST) attack attempts to disrupt an established TCP connection by sending forged reset (RST) packets to one or both communicating systems. Because a valid RST packet instructs a device to immediately terminate a connection, attackers may use this technique to interrupt legitimate communications, disrupt services, or interfere with ongoing network sessions. For analysts, the objective is to determine whether unexpected connection resets reflect normal network behavior, legitimate administrative activity, or an attempt to disrupt or manipulate communications.

Patterns: TCP Reset attacks often involve unexpected connection terminations during otherwise normal communication. Analysts may observe reset packets appearing at unusual points within a session, repeated connection interruptions, or applications repeatedly attempting to re-establish connections after they are unexpectedly closed. When successful, these attacks can produce intermittent connectivity issues that initially resemble ordinary network instability.

Indicators: Analysts may observe unexpected RST packets that do not align with the normal flow of a TCP session in packet captures or connection logs. Repeated resets affecting a particular application or system may also appear in endpoint telemetry, while IDS alerts can identify reset activity that matches known disruption patterns. While these indicators may suggest an attempt to disrupt TCP communications, they do not confirm that a TCP Reset attack is occurring. Network devices, firewalls, application timeouts, configuration changes, or legitimate protocol behavior can also generate reset packets. Analysts should examine the affected sessions, systems, and timing of the resets alongside other network evidence before determining whether the interruptions reflect malicious attempts to disrupt communications or an underlying network, application, or configuration issue.

Session Hijacking

Session hijacking occurs when an attacker attempts to take control of an established TCP session by intercepting or manipulating an active connection between two systems. Rather than creating a new connection, the attacker seeks to impersonate one of the communicating parties to gain unauthorized access or perform actions within an existing session. Although modern encryption and secure application protocols have made traditional session hijacking more difficult, understanding how attackers attempt to interfere with established TCP sessions remains valuable for analysts. Recognizing these techniques can help analysts identify abnormal connection behavior and better understand the security mechanisms that protect modern communications. For analysts, the objective is to determine whether unexpected session behavior reflects normal network conditions, legitimate administrative activity, or an attempt to interfere with an established connection.

Patterns: Session hijacking often involves attempts to inject forged packets into an established TCP session or manipulate sequence numbers to disrupt or assume control of the connection. Depending on the attack method, analysts may observe unexpected TCP reset (RST) packets, duplicate acknowledgments, abnormal sequence number behavior, or sudden interruptions to otherwise stable network sessions. These anomalies may also coincide with unusual authentication events or unexpected changes in user activity.

Indicators: Analysts may observe unexpected TCP reset (RST) packets, irregular sequence or acknowledgment numbers, or traffic that is inconsistent with the normal flow of an established session in packet captures. Authentication logs and endpoint telemetry may provide additional evidence when disrupted connections coincide with suspicious account activity or unexpected changes in user behavior. While these indicators can suggest an attempt to interfere with an active session, they do not confirm that session hijacking is occurring. Network instability, application errors, routing changes, or legitimate connection resets can produce similar observations. Analysts should correlate session anomalies with authentication activity, endpoint behavior, and other available evidence before determining whether the observed changes indicate an attempt to interfere with an established session or a legitimate disruption of the connection.

UDP Attack Patterns

UDP Floods

A UDP flood is a DoS attack that attempts to overwhelm a target by sending large volumes of UDP traffic. Unlike TCP, UDP does not establish connections or verify that packets are received, allowing attackers to generate high volumes of traffic with minimal communication overhead. As network bandwidth or system resources become saturated, legitimate users may experience degraded performance or lose access to affected services. For analysts, the objective is to determine whether elevated UDP traffic reflects expected network activity or an attempt to disrupt the availability of network services.

Patterns: UDP floods typically generate sustained, high-volume UDP traffic directed at one or more systems or services. Analysts may observe a significant increase in packets targeting specific UDP ports or multiple ports simultaneously, often with little or no corresponding application activity. During distributed attacks, the traffic may originate from multiple source IP addresses, making it appear to come from many systems simultaneously.

Indicators: Analysts may observe unusually large volumes of UDP traffic, increased bandwidth utilization, or a sudden rise in traffic directed at specific UDP services through network flow data, firewall logs, or packet captures. While these indicators may be consistent with a UDP flood, they do not confirm that one is occurring. Legitimate events such as software updates, media streaming, backups, large file transfers, or temporary spikes in network activity can produce similar observations. Analysts should correlate traffic volume with affected services and surrounding network conditions before determining whether the activity represents a deliberate attempt to exhaust resources or an unusual but legitimate increase in demand.

UDP Amplification Attacks

A UDP amplification attack is a DoS attack that abuses legitimate UDP services to generate significantly larger responses than the original requests. Attackers typically spoof the victim's IP address and send small requests to publicly accessible services, causing those services to send much larger responses to the victim instead. This amplification allows attackers to generate large volumes of traffic while minimizing their own bandwidth usage. For analysts, the objective is to determine whether unusually large volumes of UDP traffic result from legitimate service activity or an amplification attack targeting the organization.

Patterns: UDP amplification attacks often involve large numbers of small requests sent to amplification services such as DNS, NTP, SSDP, or CLDAP that generate much larger responses. Analysts may observe unusually high volumes of UDP traffic directed at a target, disproportionate request-to-response sizes, or traffic involving services commonly abused for amplification. During distributed attacks, the traffic often originates from many different systems simultaneously, making the attack appear to come from numerous legitimate servers.

Indicators: Analysts may observe unusually large volumes of inbound UDP traffic, response traffic that greatly exceeds the corresponding request size, or spikes involving commonly abused UDP services through network flow data or packet captures. These observations can help identify an amplification pattern, particularly when response traffic is substantially larger than the associated requests. Legitimate high-volume services, content delivery, or temporary increases in network activity can produce similar observations. Analysts should examine the relationship between incoming responses, the services generating them, and any corresponding requests before determining whether the traffic reflects legitimate service activity or an amplification attack.

UDP Port Scanning

A UDP port scan is a reconnaissance technique used to identify UDP services running on a target system before attempting further activity. Because UDP is connectionless, determining whether a port is open or closed is often less straightforward than with TCP. An open TCP port generally responds as part of the connection process, while UDP provides no connection state to indicate why a probe received no response. Analysts therefore need to consider the absence of a response alongside returned ICMP messages and other available evidence when evaluating UDP scan activity. For analysts, the objective is to determine whether the observed scanning activity represents expected administrative behavior or unauthorized reconnaissance.

Patterns: UDP port scans typically generate connection attempts across multiple UDP ports on one or more target systems within a short period. Depending on where the activity is observed, analysts may notice a single source probing numerous UDP ports on an individual endpoint or the same UDP ports being probed across multiple systems from a single source. The activity often follows a sequential or otherwise systematic pattern that differs from normal application traffic.

Indicators: Analysts may observe repeated UDP packets targeting multiple ports, numerous ICMP "Port Unreachable" messages, or activity involving UDP services with little expected application traffic through network flow data, endpoint telemetry, or packet captures. These observations may suggest reconnaissance, particularly when probing follows a sequential or systematic pattern across multiple ports or systems. Vulnerability scanners, asset discovery tools, network administrators, and authorized penetration tests often generate similar traffic. Analysts should correlate the probing activity with known scanning tools, authorized assessments, and the systems being targeted before determining whether the activity represents expected reconnaissance or an unauthorized attempt to identify available UDP services.

Analysis & Practical Exercises

Understanding how TCP and UDP function is only the first step. During investigations, analysts rarely rely on a single packet, log entry, or alert to determine whether activity is malicious. Instead, they examine and correlate information from multiple sources to build a more complete picture of the activity and determine whether it represents normal network behavior, a misconfiguration, or potentially malicious activity. The exercises below provide opportunities to apply these concepts using common sources of network and endpoint information while exploring how defensive controls can also affect the traffic and evidence available to an analyst.

Firewall and Network Device Logs

Once suspicious TCP or UDP activity has been identified, firewall and network device logs are often the first source analysts examine because they provide a centralized record of network communications occurring throughout the environment. These logs capture connection attempts, protocols, ports, source and destination systems, and the actions taken by network security devices, allowing analysts to identify abnormal communication patterns before pivoting to packet captures, endpoint telemetry, or other evidence sources. Because most network traffic passes through these devices, firewall and network logs frequently provide some of the earliest evidence of suspicious transport-layer activity.

Key Information:

  • Source IP address – Identifies the system initiating the communication.
  • Destination IP address – Identifies the intended recipient of the traffic.
  • Protocol (TCP or UDP) – Indicates which transport protocol was used.
  • Source and destination ports – Identify the services or applications involved in the communication.
  • Connection action (allowed, denied, reset, etc.) – Shows how the firewall or network device handled the traffic.
  • Session details – May include connection duration, bytes transferred, connection state, or other metadata depending on the device.

Common Findings:

  • Repeated connection attempts across multiple ports or systems that may indicate reconnaissance or port scanning.
  • Significant increases in TCP or UDP traffic directed toward a specific host or service that may suggest denial-of-service activity.
  • Unexpected communication using uncommon ports or protocols that differs from normal network behavior.
  • Blocked or denied connections involving unauthorized services, restricted ports, or suspicious external systems.

Skill Builder: Review firewall logs from a home router, firewall appliance, virtual firewall, home lab, or publicly available sample dataset. Generate normal network activity by browsing websites, resolving DNS queries, or connecting to another device in your lab, then identify the source and destination addresses, ports, protocols, and actions recorded in the logs. If you have access to a virtual machine, perform a basic TCP or UDP scan against that system using Nmap and compare how the resulting activity differs from routine network traffic.

SIEM and Log Correlation

Transport-layer activity rarely provides enough evidence to determine whether an event is malicious on its own. Analysts use Security Information and Event Management (SIEM) platforms to correlate firewall logs, intrusion detection alerts, endpoint telemetry, authentication events, and other security data to build a more complete picture of network activity. This broader perspective helps analysts distinguish isolated events from larger attack patterns while reducing the likelihood of drawing conclusions from a single source of evidence.

Key Information:

  • Correlated firewall events – Reveal communication patterns across multiple systems.
  • IDS/IPS alerts – Highlight suspicious network behavior associated with known attack techniques.
  • Endpoint telemetry – Associates network activity with specific processes or users.
  • Authentication events – Help determine whether suspicious network activity coincides with account activity.
  • Event timelines – Show how related events occur before, during, and after suspicious communications.

Common Findings:

  • Multiple related alerts that reveal reconnaissance followed by exploitation attempts.
  • Correlated network and endpoint activity indicating the same system is involved in multiple suspicious events.
  • Repeated connection attempts occurring across numerous hosts within a short period.
  • Network events that appear suspiciou s individually but are explained by scheduled maintenance, vulnerability scans, or authorized administrative activity.

Skill Builder: Download a publicly available SIEM dataset, such as Splunk's Boss of the SOC (BOTS) dataset, or sample log files and import them into a SIEM or log-analysis platform. Identify related events involving the same system or connection and build a simple timeline showing how firewall events, endpoint activity, and authentication records support or contradict one another.

Packet Captures and Protocol Analysis

Packet captures provide the most detailed view of TCP and UDP communications by allowing analysts to examine individual packets exchanged between systems. Unlike logs that summarize activity, packet captures reveal how communication actually occurred, making them valuable for validating suspicious behavior and answering questions that other evidence sources cannot. Analysts frequently use packet analysis to confirm attack patterns, identify protocol anomalies, and understand the sequence of events during an investigation.

Key Information:

  • TCP handshakes – Confirm whether connections were successfully established.
  • TCP flags – Help identify connection setup, termination, and abnormal behavior.
  • Sequence and acknowledgment numbers – Reveal communication flow and possible manipulation.
  • Retransmissions and resets – May indicate connectivity issues or attempts to disrupt communications.
  • UDP datagrams – Show connectionless communication and traffic patterns.

Common Findings:

  • Successful TCP handshakes associated with legitimate application traffic.
  • Incomplete handshakes or excessive SYN packets that may indicate scanning or denial-of-service activity.
  • Unexpected TCP reset packets or abnormal retransmissions.
  • UDP traffic patterns that differ significantly from expected application behavior.

Skill Builder: Capture network traffic using Wireshark while browsing websites, performing DNS lookups, or connecting to another system in a home lab. Identify TCP handshakes, observe the differences between TCP and UDP communications, and compare the packet-level activity with the corresponding firewall logs or connection records.

Endpoint / EDR Telemetry

Network traffic explains how systems communicate, but endpoint telemetry explains what was happening on the system that generated the communication. Endpoint Detection and Response (EDR) platforms and operating system logs help analysts associate TCP and UDP activity with specific processes, services, users, and applications. Combining endpoint and network evidence allows analysts to determine whether observed communications are consistent with expected system behavior or require additional investigation.

Key Information:

  • Running processes – Identify which application initiated the communication.
  • Parent-child process relationships – Provide context surrounding process execution.
  • Network connections – Associate active communications with specific applications.
  • Listening services – Identify applications accepting inbound connections.
  • User context – Helps determine who initiated the activity.

Common Findings:

  • Legitimate applications communicating over expected ports.
  • Administrative tools generating authorized network activity.
  • Unexpected processes establishing external communications.
  • Malware or unauthorized software creating network connections inconsistent with normal system behavior.

Skill Builder: Use operating system tools such as netstat, ss, or Get-NetTCPConnection to identify active TCP and UDP connections on your computer. Match those connections to the processes that created them using Task Manager, Resource Monitor, or similar utilities, then examine the associated process and user context to determine whether the observed activity matches what you expected the system to be doing.

Network Security Controls

Security controls do more than generate evidence for analysts to investigate; they also influence how network traffic is allowed, blocked, or modified as it moves through the environment. Firewalls, intrusion prevention systems, access control lists, segmentation, and other enforcement mechanisms can change the traffic that reaches a destination and the evidence available to an analyst. Understanding these effects helps analysts evaluate network activity in context and recognize when defensive controls may contribute to false positives, limit visibility, or require refinement.

Key Information:

  • Firewall policies – Control which communications are permitted or denied.
  • Access control lists (ACLs) – Restrict traffic between networks, systems, or services.
  • Intrusion detection and prevention systems (IDS/IPS) – Detect or block suspicious transport-layer activity.
  • Network segmentation – Limits communication between systems to reduce attack paths.
  • Traffic filtering and rate limiting – Help protect services from excessive or unauthorized communications.

Common Findings:

  • Blocked connection attempts targeting restricted services or ports.
  • IDS/IPS alerts identifying suspicious transport-layer behavior.
  • Traffic denied because of segmentation or firewall policy.
  • Rate-limited communications associated with excessive connection attempts or denial-of-service activity.

Skill Builder: If you have access to a home firewall, virtual firewall, or router with configurable rules, create a rule that blocks or allows a specific TCP or UDP port and observe how the resulting network activity changes. If you do not have access to a configurable firewall, review documentation or demonstrations of common firewall rules and predict how those rules would affect the TCP or UDP communications discussed throughout this article.

SOC Analyst Perspective

Understanding how TCP and UDP function is only part of network analysis. The next step is learning how to apply that knowledge during an investigation. Alerts provide a starting point, but they rarely identify the root cause of suspicious activity on their own. Analysts must validate the reported behavior, examine the available evidence, and determine whether the observed activity is consistent with normal network operations or indicates malicious behavior. The workflows below demonstrate a structured approach to investigating several common TCP and UDP attack patterns. While the examples discuss potential mitigation strategies, organizational procedures determine whether analysts implement containment measures directly or document their findings and escalate the incident to other teams. Understanding your organization's roles, responsibilities, and incident response procedures is an essential part of effective security operations.

Investigating Suspected SYN Flood Activity

SYN flood activity can place enough incomplete connections on a server to interfere with legitimate TCP sessions. In an investigation, however, observing this behavior does not establish that the system is under attack. Similar connection patterns can result from temporary traffic spikes, network congestion, or misconfigured applications.

First — Identify systems generating unusually high numbers of incomplete TCP connection attempts.

Begin by identifying the systems associated with the alert and determine whether they are generating significantly more incomplete TCP handshakes than similar systems during the same time period. Compare the volume and distribution of incomplete connection attempts against the system's normal behavior to determine whether the activity is unusual for that environment. As you characterize the activity, consider whether the connection attempts are concentrated on a single destination, distributed across multiple systems, or sustained over an extended period. These observations establish the scope of the activity and help determine whether the alert warrants deeper investigation.

Then — Examine the connection patterns.

Evaluate whether the incomplete connection attempts follow patterns consistent with legitimate traffic surges, application behavior, or an attempt to exhaust server resources. Correlate the observed connection attempts with packet captures, connection logs, firewall activity, or other available evidence to determine whether TCP handshakes are routinely left incomplete, whether retransmissions or repeated attempts occur, and whether legitimate users are successfully establishing new connections. Together, these observations help determine whether the activity is consistent with normal network conditions or with an attempt to exhaust server resources by preventing new TCP connections from being established.

Finally — Determine the appropriate mitigation.

Focus on reducing the volume of incomplete connection attempts while preserving the service's ability to accept legitimate TCP connections. Depending on the environment, this may include enabling SYN cookies, implementing rate limiting, adjusting firewall protections, or using other controls designed to reduce the effect of connection-exhaustion attacks. For example, SYN cookies allow a server to avoid allocating resources for every incomplete connection until the handshake is completed, reducing the ability of a large volume of SYN requests to exhaust connection resources. Once a control is in place, observe the affected service and traffic patterns to determine whether incomplete connections have decreased, legitimate connections are completing normally, and whether additional activity suggests that the attack is continuing or changing.

Investigating Suspected TCP Port Scanning

TCP port scanning can reveal which services are accessible on a system or across a network, but the significance of that activity depends on what is being scanned and why. Authorized discovery and assessment tools can produce patterns similar to reconnaissance, so the same scanning behavior may have very different implications depending on the systems involved and the activity expected from them. This makes the surrounding context important when evaluating whether observed probing is consistent with legitimate network activity or warrants further investigation.

First — Identify systems exhibiting unusual TCP connection attempts across multiple ports or hosts.

Begin by identifying the systems associated with the alert and determine whether they are attempting TCP connections to an unusually large number of destination ports, multiple hosts, or both during the same time period. Compare the connection patterns generated by the affected systems against similar systems performing the same role to determine whether the observed behavior is unusual for that environment. As you characterize the activity, determine whether the connections are focused on a small number of systems, distributed across many systems, targeting a broad range of ports, or concentrating on specific services. These observations establish the scope of the activity and help determine whether the alert warrants deeper investigation.

Then — Examine the scanning behavior.

Once the scope of the activity has been established, examine how the connection attempts are being performed. Determine whether the activity is focused on a large number of ports on a single host (vertical scanning), the same port across multiple hosts (horizontal scanning), or a combination of both. Evaluate what the connection outcomes reveal about the targeted systems, such as which services appear to be exposed, whether multiple systems share similar service profiles, and whether the activity appears to be building an inventory of network-accessible services or searching for a specific target. Consider whether the observed scanning patterns and the information being gathered are more consistent with authorized administrative activities, automated vulnerability assessments, or reconnaissance intended to identify potential targets for future exploitation. Together, these observations help determine whether the activity represents expected administrative behavior or unauthorized reconnaissance requiring further investigation.

Finally — Determine the appropriate mitigation.

The goal is to reduce unnecessary exposure without disrupting legitimate administrative scanning or services that need to remain accessible. If the investigation identifies an exposed service that does not need to be reachable from the scanning source or network, restricting access to that service can reduce the information available to the scanner. This could involve adjusting firewall rules, limiting access to specific networks or hosts, or disabling an unnecessary service, depending on what the investigation reveals. The resulting network activity can then show whether reconnaissance has been reduced or whether the source has shifted its scanning to other systems or services.

Investigating Suspected UDP Amplification Activity

Large volumes of UDP traffic can be difficult to interpret when legitimate services are capable of generating substantial response traffic. In an investigation, the analyst needs to determine whether the traffic is consistent with expected service behavior or whether the organization is receiving traffic that it did not request. The volume, direction, and relationships between the systems involved therefore become important when determining whether the activity warrants further investigation.

First — Identify systems generating or receiving unusually asymmetric UDP traffic.

Begin by identifying the systems associated with the alert and determine whether they are sending or receiving unusually large volumes of UDP traffic during the same time period. Compare the volume and direction of the observed traffic against similar systems performing the same role to determine whether the behavior is unusual for that environment. As you characterize the activity, determine whether the traffic is concentrated between a small number of systems or distributed across many sources or destinations, whether it targets one service or several, and whether the activity represents a brief spike or a sustained pattern. These observations establish the scope of the activity and help determine whether the alert warrants deeper investigation.

Then — Examine the traffic relationships.

Once the scope of the activity has been established, evaluate what the observed traffic patterns reveal about the systems involved. Determine whether the traffic suggests that the affected host is receiving responses without the associated requests, whether intermediary systems appear to be reflecting traffic toward another destination, or whether specific UDP services are generating disproportionately large responses from relatively small requests. Consider whether the observed communication patterns are more consistent with legitimate application behavior, expected high-volume UDP services, or an attempt to use connectionless protocols to reflect or amplify traffic toward a victim. Together, these observations help determine whether the activity represents expected network behavior or a reflection or amplification attack requiring further investigation.

Finally — Determine the appropriate mitigation.

Focus on reducing the amount of unwanted reflected or amplified traffic reaching the affected system while preserving legitimate UDP communication. The volume and characteristics of the attack may determine whether rate limiting unwanted UDP traffic, filtering traffic associated with the attack, restricting exposed UDP services that can be abused for reflection or amplification, or coordinating with an upstream provider is most appropriate. A rate limit, for example, can prevent excessive UDP traffic from consuming all available resources while still allowing legitimate communication to reach the service. The response should be assessed by looking at whether the attack traffic has decreased and whether the affected service has returned to normal operation, while remaining alert for changes in the sources, volume, or characteristics of the traffic.

Investigating Suspected UDP Port Scanning

UDP scanning can produce ambiguous results because the absence of a response does not necessarily explain what is happening on the targeted port. The same probing behavior can therefore require different interpretations depending on the systems involved, the services expected on those ports, and the responses generated during the scan. This makes context particularly important when determining whether the activity reflects legitimate service discovery or reconnaissance that warrants further investigation.

First — Identify systems generating unusual UDP probes across multiple ports or hosts.

Begin by identifying the systems associated with the alert and determine whether they are sending UDP probes to an unusually large number of destination ports, multiple hosts, or both during the same time period. Compare the observed activity against similar systems performing the same role to determine whether the behavior is unusual for that environment. As you characterize the activity, determine whether the probes are concentrated on a small number of systems, distributed across many systems, targeting a broad range of ports, or focused on particular services. These observations establish the scope of the activity and help determine whether the alert warrants deeper investigation.

Then — Examine the available evidence and determine what conclusions can reasonably be drawn.

Evaluate the responses associated with the UDP probes and consider what they reveal about the targeted systems. Look for application responses, ICMP Port Unreachable messages, and unanswered probes, while recognizing that the absence of a response does not by itself establish that a UDP service is closed. Compare the targeted ports and systems with known services and expected administrative activity to determine whether the scan appears to be identifying available UDP services, searching for a particular service, or occurring as part of an authorized assessment. Together, these observations help determine whether the activity represents expected network behavior or unauthorized reconnaissance requiring further investigation.

Finally — Determine the appropriate mitigation.

Focus on reducing unnecessary UDP exposure and limiting the information that an unauthorized scan can reveal about available services. The appropriate action may include disabling unnecessary UDP services, restricting access to required services, or adjusting firewall rules to limit which systems or networks can reach them. For example, if a scan identifies an unnecessary UDP service exposed to an untrusted network, removing that exposure reduces both the service's attack surface and the information available to future reconnaissance. Subsequent scans and network activity can help determine whether the exposure has actually been reduced and whether reconnaissance has shifted to other systems, ports, or services.

While the specific steps vary depending on the alert and the environment, effective TCP and UDP investigations rely on interpreting network behavior within its broader context rather than drawing conclusions from a single observation. Analysts build confidence in their findings by validating alerts, correlating available evidence, considering both legitimate and malicious explanations, and using what they learn to determine an appropriate response. This evidence-based approach helps analysts distinguish expected network behavior from genuine threats while recognizing that mitigation is part of an ongoing investigation rather than necessarily its conclusion.

Conclusion

Understanding the distinct behaviors of TCP and UDP—TCP's connection-oriented, handshake-based communication versus UDP's connectionless datagram exchange—helps SOC analysts recognize unusual network activity and investigate whether observed patterns represent legitimate communication or malicious behavior. This knowledge can improve triage speed, reduce false positives, and support more effective responses during incident investigations. Recognizing these protocol differences gives analysts a basis for interpreting the network evidence behind security alerts rather than treating individual packets or connections in isolation.

That foundation allows analysts to interpret network activity across the evidence sources they encounter in security operations, including firewall logs, packet captures, and IDS alerts. Recognizing protocol-specific anomalies can help analysts move more quickly from detection to investigation, correlating network data with endpoint telemetry to validate what they are seeing and determine whether additional evidence is needed. The same analytical skills provide a foundation for more advanced defensive work, including threat hunting, incident response, and digital forensics and incident response (DFIR).

Developing these skills requires continued practice with real network data. Working with Wireshark packet captures and Zeek connection logs can reinforce TCP and UDP behavior while building the analytical skills needed for IDS rule analysis and SIEM alert triage. Applying the same approach to additional protocols and network technologies will expand the analyst's ability to recognize patterns, investigate anomalies, and understand the security significance of network behavior across different environments.
