DNS in the SOC: From Name Resolution to Detection Opportunities

A practical SOC analyst guide to recognizing DNS attack patterns in packet captures, logs, and SIEM alerts.

Domain Name System (DNS) is often described as the “phonebook” of the internet, mapping human‑friendly domain names to IP addresses so clients can find resources across networks. This naming layer is what allows users to type example.com instead of memorizing IPs and still reach web servers, APIs, or internal applications. When DNS was originally designed, its creators did not anticipate modern attackers abusing its open, unauthenticated nature, or defenders trying to monitor it for subtle signs of compromise.

As environments grew more complex, DNS became deeply embedded in how operating systems, applications, and services discover each other. Today, adversaries misuse DNS for command‑and‑control (C2) communication, data exfiltration, phishing infrastructure, and domain‑generation algorithms (DGAs), while defenders treat DNS logs and traffic patterns as a critical source of detection signals. At the same time, DNS is essential to normal network operations and cannot simply be blocked or disabled, which makes understanding normal behavior—and how attackers twist it—especially important for early‑career defenders.

Security enhancements like DNS over TLS (DoT), DNS over HTTPS (DoH), and DNS Security Extensions (DNSSEC) were introduced to protect different parts of the DNS ecosystem, but they do not replace the need to understand plain DNS behavior. This guide takes a practical view of DNS from a defender’s perspective, connecting core concepts to common abuse patterns and the kinds of evidence you will see in logs and network data during real investigations.

What DNS Is

DNS separates human friendly names from IP addresses. Instead of applications talking directly in IPs, they ask DNS “what IP should I use for this name?”, then use the answer to connect.

From a SOC analyst’s perspective, DNS is not just a convenience service; it is a structured record of who tried to look up what, and when. Each query captures a client (source IP or host), a name, a record type, and a response code, all of which can become useful detection signals during triage and hunting.

Concept Breakdown: How DNS Works

This is the “just enough” version; your separate fundamentals article can cover the full resolver flow.

Key Roles:

• Stub resolver OS component on the client that forwards DNS queries for applications.

• Recursive resolver – DNS server your client points to (organizational or ISP). It finds answers and caches them.

• Authoritative name servers – Servers that hold the official records for a domain (for example, the authoritative servers for example.com).

High level flow 1. Client asks its configured resolver for a record (for example, the A record for www.example.com). 2. Resolver checks its cache; if it has a valid answer, it responds immediately. 3. If not cached, resolver walks the hierarchy (root → TLD like .com → authoritative server for the domain) to get the answer. 4. Resolver returns the answer to the client and caches it for the time to live (TTL). As an analyst, you rarely see each hop, but you frequently see the resulting queries and answers in DNS or SIEM logs. Common record types in logs • A / AAAA – Map a name to an IPv4 (A) or IPv6 (AAAA) address. • CNAME – Alias from one name to another (for example, www.example.com → app.example.com). • MX – Mail exchange; where to deliver email for a domain. • NS – Name server; which servers are authoritative for a zone. • TXT – Free form text (SPF/DMARC, verification); can also be abused for tunneling or attacker controlled data. Encrypted DNS and DNSSEC • DNS over TLS (DoT) – DNS queries/responses carried over a TLS encrypted channel, typically port 853; hides contents from intermediaries and makes tampering detectable. • DNS over HTTPS (DoH) – DNS queries sent inside HTTPS (usually port 443); similar protection to DoT but mixed into normal web traffic, complicating some monitoring and blocking approaches. • DNSSEC – Adds cryptographic signatures so resolvers can verify that responses came from the legitimate authoritative servers and were not modified (for example, cache poisoning). It does not encrypt DNS; it protects authenticity and integrity, not confidentiality. For this guide, the key takeaway is: DoT and DoH encrypt DNS in transit; DNSSEC helps you trust that answers are genuine. All three change where and how defenders can observe DNS behavior, but they do not remove DNS as a detection surface.
